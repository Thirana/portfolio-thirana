# Drydock

Drydock is a guide to how networks work, in three steps: a networking fundamentals course, a course on networking in Google Cloud, and Harbour - a fictional platform on Google Cloud whose network I misconfigured on purpose. I built it while working through Google Cloud networking end to end. The courses teach the concepts, and Harbour tests them.

## The two courses

Both courses follow **Kadé**, a small online grocery shop in Colombo. The reader is its backend engineer. Chapter 0 of each course holds the story, the network map and an address book, and every later chapter uses those same addresses.

- **Fundamentals** follows one request from a laptop on home Wi-Fi to a server: addressing, ARP, NAT, routing, TCP and UDP, DNS, HTTP, TLS, and the proxies and load balancers in between.
- **Networking on GCP** moves Kadé into Google Cloud: VPCs, firewall rules and policies, IAP, Cloud NAT, private access, Cloud Run, load balancing, Cloud Armor, Cloudflare, hybrid links and governance.

Most chapters have an interactive widget, such as a CIDR calculator, a DNS resolution simulator or a TCP congestion window simulator.

## Harbour: a platform built wrong on purpose

Harbour is a fictional marketplace for independent sellers. Four paths keep it running: shoppers loading product pages, checkout charging the card through a payment gateway, a nightly job paying sellers, and a courier reading order status over a private link. Each of its 17 defects started as a reasonable shortcut that nobody revisited, such as SSH opened to the internet so the founders could deploy from anywhere.

Each defect page has the symptom, the impact, the command that finds it, what blocks the fix, the state before and after, and the change that closes it.

<CodeToggle title="Show the command that finds D1">

```bash
# D1 - ingress rules open to the whole internet
gcloud compute firewall-rules list --format="table(
  name,priority,direction,sourceRanges.list(),targetTags.list(),
  allowed[].map().firewall_rule().list())" \
  --filter="direction=INGRESS AND sourceRanges:0.0.0.0/0"
```

## The order of the fixes

A list of 17 findings does not say where to start. Several fixes cannot begin until another one is finished, so Harbour fixes them in six phases:

<Diagram
  src="/diagrams/projects/drydock/fix-order.svg"
  alt="Six phases from left to right: 1 Groundwork, 2 Secure access, 3 Close the bypasses, 4 Private data path, 5 Egress and load balancer, 6 Govern and tighten. Each defect sits under the phase that fixes it, colored by severity. Arrows show what has to be fixed first: D12 before D13 and D14, D4 and D5 before D3b, D2 before D3a and D16, and D2, D6 and D9 before D1, which is deleted last once nothing relies on it."
  width={718}
  height={508}
  caption="Each arrow points from a fix to the one it unblocks"
/>

- **Add before removing.** The IAP-only SSH rule is tested on every VM before the open SSH rule is deleted. In the other order, every engineer is locked out.
- **The legacy VMs keep their public IPs until phase 4.** They use them to reach Google APIs and the database, so the IPs can only go once Private Google Access is on and Cloud SQL has a private IP.
- **The allow-all rule goes last.** Deleting it shows what was relying on it, so every service first needs its own narrow rule, checked VM by VM.

## Following the traffic

Six packet journeys trace one request hop by hop: a product page, a health check, a card charge, the nightly job, an SSH session and the partner reaching the database. Each journey and each defect can be viewed as found or fixed, and a phase rail on the map moves the whole platform through the sequence.

Harbour is fictional. It is not a production template or an audit of a real system, and its names and addresses are invented. More Harbour tracks, such as IAM, are planned.
